BO — Cosa cambierei riscrivendolo da zero & come renderlo più veloce

In sintesi

Risposta onesta: non lo riscriverei da zero. Lo stack (NestJS + Prisma + Postgres + React) è adeguato alla scala, ci sono 113k righe di test su 119k di codice (ratio ~1:1, rarissimo) e un team di 4 non può congelare lo sviluppo per mesi. Però ci sono 7 scelte che cambierei, tutte attuabili in modo incrementale (una capability alla volta, senza fermare il BO). Sul fronte velocità: il 60-70% del carico DB non viene dal BO ma dal sito pubblico, e le 3 cause principali di lentezza sono tutte fixabili in giorni, non mesi.

Parte 1 — Le 7 cose che cambierei (con vantaggi)

1. La doppia verità eventi/stato → una sola proiezione impatto alto

Evidenza: il BO è "event-driven": ogni azione scrive un Event append-only (2,2M righe). Ma lo stato è anche copiato in colonne della tabella RFQ (status, hasOrder, lastClientPrice…). Prova che le due verità divergono: esistono funzioni di riparazione syncRfqHasOrderFromTimeline e syncLastClientPriceFromTimeline (rfq.service.ts:10835/10881) — se non divergessero mai, non servirebbero. A ogni apertura RFQ lo stato viene ri-calcolato rileggendo tutti gli eventi.

Da zero farei: eventi append-only (come oggi, funziona) + tabella RfqProjection aggiornata nella stessa transazione dell'evento. Replay solo per repair/debug.

Vantaggi: dettaglio RFQ = 1 query invece di replay; sparisce la divergenza (e le funzioni "sync"); timeline invariata per l'utente.

2. rfq.service.ts: 24k righe / 189 metodi → 8 service per capability impatto alto

Evidenza: il file più grosso è il 20% dell'intero backend e il più modificato (297 commit/6 mesi = ogni feature passa di lì). Contiene 7 metodi retry*BusinessMail quasi identici, 95 endpoint nel controller, 12 servizi iniettati.

Da zero farei: split per capability: RfqLifecycle, RfqOffer, RfqMail, RfqLinks, RfqQueries, RfqContacts, RfqCopilot, RfqWebsite.

Vantaggi: PR piccole e reviewabili (oggi ogni modifica = stesso file da 24k righe, conflitti garantiti); test per capability; anche Codex/agenti AI editano file da 2-3k righe in modo drasticamente più affidabile che uno da 24k — rilevante per il nostro workflow.

3. Parser: v1 (17k righe flat) + v2 (6k, pipeline) → solo v2, sender come config impatto alto

Evidenza: esiste già una v2 ben architettata (pipeline p0→p6: normalize → marker → source → llm → product → client → open-rfq). Il v1 convive: 40 file flat, deterministic-apply.ts da 4k righe. I 16 parser per-mittente sono fork di codice (123-174 righe ciascuno).

Da zero farei: v2 unica pipeline; per-sender = file di config (regex, override campi, fixture), non codice.

Vantaggi: allineato alla tua priorità #1 (accuratezza parser): le 2 root cause trovate il 18/10 (domain fallback, product matching) diventano fix puntuali in p5-client/p4-product invece che sparse nel flat; un nuovo fornitore = ~50 righe di config, non un branch.

4. Feature flag sparsi → config tipata centrale medio-alto

Evidenza: 139 letture process.env sparse; la flag PARSER_FREE_SCAN_MULTI_PRODUCT è letta in 34 punti con parsing inline duplicato. Ci abbiamo già perso due volte ("deploy ≠ attivo in prod": 15/10 e 18/10).

Da zero farei: modulo TypedConfig (env validata all'avvio) + FeatureFlagsService con override da tabella AppConfig (esiste già!) + endpoint/pagina "stato flag in prod".

Vantaggio: verifica "la flag è ON?" in 10 secondi da schermata, non con query a mano. Sforzo piccolo (S).

5. Frontend: pagine-mostro e zero infrastruttura dati impatto alto

Evidenza: RfqDetailPage.tsx = 8.540 righe, 108 useState, 24 useEffect, ~10 fetch separati all'apertura. InboxPage 6.125 righe. Nessuna libreria di stato o data-fetching (tutto manuale), nessuna virtualizzazione liste (6.689 righe inbox renderizzate nel DOM), 7.781 righe di test per una sola pagina = fa troppo. Nota positiva: 105 route lazy + layer API condiviso esistono.

Da zero farei: react-query (cache, dedup, refetch automatici) + decomposizione pagine in componenti/hooks + react-window sulle liste.

Vantaggi: inbox smette di bloccare il browser; le azioni smettono di ricaricare tutto; i test si dimezzano perché la logica esce dalle pagine.

6. Confini di modulo non enforced medio

Evidenza: 56 moduli, ma cross-import diffusi (rfq importa 11 servizi esterni, whatsapp/awaitRequests "opzionali" nel god-service); 24 file .spec.ts orfani nella root di src/.

Da zero farei: ESLint no-restricted-paths in CI: un service importa solo dal proprio modulo o da common.

Vantaggio: la regola "Giovanni solo per strutturali" diventa verificabile meccanicamente: una PR che tocca confini di modulo salta all'occhio da sola.

7. Tabella Event: 3,6 GB con 16 indici (4 morti) e 2 colonne-tempo duplicate medio

Evidenza (DB live): Event = 2,4 GB tabella + 1,1 GB di indici. Event_actorId_idx 2 scansioni (32 MB), causationId 1 (27 MB), correlationId 92 (48 MB), traceId 2.031 (48 MB). Coppie duplicate timestamp+occurredAt indicizzate entrambe. Ogni insert evento aggiorna 16 indici.

Da zero farei: una sola colonna tempo; drop indici morti (~155 MB + write amplification); retention: eventi legacy 2006-2020 archiviabili in tabella fredda.

Vantaggio: insert più veloci (il parser scrive migliaia di eventi/giorno), backup più leggeri.

Cosa NON cambierei

  • Stack NestJS+Prisma+Postgres+React: adeguato, nessun collo strutturale.
  • Event model append-only: 13,1 eventi/RFQ in media (p95=44) → il replay non è il collo di bottiglia, il problema è solo la doppia verità (punto 1).
  • Cultura test 1:1 — asset raro, da preservare sopra ogni refactor.
  • Direzione parser v2 e 105 route lazy del frontend: la strada è già quella giusta.

B. Quick wins (< 1 giorno, effetto visibile)

  1. Inbox: take:100 + select senza corpi → da ~0,5 GB a KB per refresh
  2. Raw SQL Event su colonna invece di payload → 11,4s → ms
  3. compression() in main.ts: una riga, −70/90% banda API (oggi assente)
  4. Cache in-memory LegacyCategory (letta 5,27M volte × 3,9ms — tabella di poche centinaia di righe!) + tasso EUR/USD: pattern cache già usato in casa (parser-config.service.ts)
  5. 5 indici puri (solo migrazione, rischio zero): Document(rfqId) e Document(masterMessageId) — verificati mancanti: Documents ha 24,2M seq_scan vs 1M idx_scan — più RfqLink(linkedRfqId), InboxItem(isResolved, createdAt), ParseRun(masterMessageId, createdAt DESC)

C. Strutturali (via Giovanni — schema)

  • Indici Document del punto B5 (fk mancanti — verifica: la tabella ha solo indici su productId e internalNoteId, ma le query filtrano per rfqId/masterMessageId)

  • Drop indici Event morti (~155 MB, 4 indici)

D. Frontend

  • react-window sulla lista inbox (6.689 righe DOM oggi)
  • react-query: cache + dedup delle ~10 chiamate di RfqDetailPage; refetch mirati invece di reload completi

💡 Idea mia (nuova, data-backed)

Auto-resolve discussioni stale. Dei 6.689 inbox non risolti: 4.513 sono DISCUSSION e 2.209 hanno >90 giorni. Le discussioni su RFQ chiuse o senza attività da X giorni restano "aperte" per sempre, gonfiando sia la query (collo #2) sia il rumore per gli operatori. Regola: auto-resolve DISCUSSION/RFQ_THREAD se RFQ chiusa o nessun evento da 60+ giorni. Misurabile: count non-risolti e tempo query inbox prima/dopo, nel digest settimanale.

DB load nel digest del lunedì. Il digest settimanale (già attivo) può includere le top-3 query per tempo totale da pg_stat_statements: ogni deploy di questa lista (cache sito, indici) verrebbe verificato sui numeri reali la settimana dopo, chiudendo il ciclo "deploy ≠ effetto" che ci ha bruciato due volte.
