1. SICUREZZA — segnalazione originale e piano (storico, vedere verifica sopra)

Problema: un file .env di produzione è tracciato in git (nome file e commit nel memo privato — chiedere a Vittorio) e contiene:

  • SUPABASE_URL
  • SUPABASE_SERVICE_ROLE_KEY — la chiave service_role bypassa tutte le Row Level Security: chi la possiede ha accesso totale al database di produzione.

Lo stesso file è tracciato anche in due clone satellite del repo. Chiunque abbia accesso in lettura al repo — su GitHub o in locale — ha la chiave master del DB.

Piano di remediation in 5 passi:

  1. Sostituzione e revoca della chiave dalla dashboard Supabase: aggiornare gli ambienti e verificare il funzionamento, quindi confermare l'invalidazione della chiave precedente con la procedura adatta al suo tipo. La sola creazione di una nuova secret key non invalida le chiavi legacy. (Questo passo lo fate tu/Vittorio: non ho accesso alla dashboard.)
  2. Aggiornamento env + redeploy via ops/deploy-bo-prod.sh e verifica che tutto funzioni.
  3. Verifica accessi: chi ha accesso al repo GitHub; controllo dei log Supabase per uso anomalo della chiave.
  4. Pulizia git (la faccio io, col tuo GO): rimozione del file dal tracking + aggiunta di *.prod.env al .gitignore + scansione dell'intera history con gitleaks per intercettare altri segreti.
  5. (Opzionale) Purge della history con git filter-repo + force push, se vuoi eliminare la chiave anche dallo storico.
