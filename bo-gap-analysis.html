1. Autenticazione / Autorizzazione (BO + token portal)

Stato attuale (evidenze)

  • BO auth implementata: src/backend/src/backoffice-auth/ — JWT via passport (backoffice-jwt.strategy.ts), login bcrypt su User.passwordHash, token 24h, guard globale BackofficeAuthGuard registrata via APP_GUARD in backoffice-auth.module.ts, decorator @Public() per endpoint aperti. La strategy riverifica user.active a ogni richiesta (revoca efficace).
  • Ruoli: roles.guard.ts + @Roles('ADMIN'|'OPERATOR'); flag canViewReports con guard dedicata (reports-access.guard.ts). @Roles applicato su admin, users, outbox, database-backup, parser-config, whatsapp (evidenza: rg @Roles → ~10 controller). La maggior parte degli endpoint di business richiede solo autenticazione (RBAC a maglie larghe).
  • Portal auth implementata: src/backend/src/portal-auth/ — PortalAccount con bcrypt, dominio client/supplier, reset password con token sha256-hashed a scadenza 1h inviato via email (portal-auth.service.ts).
  • Token portal pubblico (link supplier/client): modules/tokens/tokens.controller.ts è @Public() con OpaqueTokenPipe (sanitizzazione token) e idempotenza via TokenActionLog.
  • Rate limiting sui login: ThrottlerGuard su login BO, login portal e forgot-password (10 req/60s).
  • Session restore + env-handoff ticket cross-environment (2 min) con segreti multipli (JWT_HANDOFF_ALT_SECRETS, ENV_HANDOFF_SECRET).
  • Frontend BO: JWT tenuto in memoria (non in localStorage — buona scelta XSS), src/frontend/src/api/client.ts.

Gap

  • README dichiara "Attualmente non c'è autenticazione (planned)" → documentazione fuorviante per chi prende in mano il progetto.
  • Password policy debole: min 6 char utenti BO (users.dto.ts), min 8 portal (portal-auth.dto.ts); nessun controllo di complessità né lockout account (mitigato solo dal throttler).
  • Nessun refresh token / sessioni multiple non gestite; logout = lato client (token 24h resta valido se copiato, salvo disattivazione utente).
  • Rate limiting non globale: ThrottlerModule.forRoot è configurato ma la guard è applicata solo su 4 endpoint auth; il resto delle API (incluse le token page pubbliche) non ha throttling applicativo.
  • Endpoint pubblici numerosi oltre ai token: health/monitoring, attachments pubblici, website-chat, discussions pubbliche — superficie da tenere sotto osservazione.

Rischio

MEDIO (auth core solida; hardening e docs da allineare).

Raccomandazione

Aggiornare README/doc; alzare password policy (min 12 + controllo banalità); valutare throttling globale (APP_GUARD ThrottlerGuard con bypass per health); audit degli endpoint @Public() con motivazione documentata; considerare lockout progressivo su login.

Effort

S (documentazione, policy, throttling) — M se si aggiungono lockout/audit completi.

2. CI/CD

Stato attuale (evidenze)

  • Nessuna pipeline CI/CD: assente .github/workflows/, nessun GitLab CI/Azure/CircleCI. Remote: GitHub privato vittorio-art/novarium-backoffice (verificato 404 anonimo → privato).
  • Deploy produzione: ops/deploy-bo-prod.sh sul server — script ben fatto: dirty-tree check, flock, git fetch + reset --hard origin/main, docker compose up -d --build, health check con verifica gitSha live, asset-hash check, file di stato deploy esposto via nginx (/__deployment_status).
  • Verifica "CI-style" solo locale/manuale: scripts/verify.sh + scripts/run-tests.sh (test, build, healthcheck con DB docker).
  • Documentazione deploy: ops/DEPLOY.md (completa e allineata).

Gap

  • Nessun gate automatico: i 254+213 test non girano in CI; si può pushare su main e deployare senza che nulla sia stato eseguito.
  • Build delle immagini avviene sul server di produzione (no registry, no artifact immutabili) → build failure = deploy failure sul live.
  • Nessun rollback automatico (rollback = revert commit + re-deploy manuale).
  • Deploy dipendente da accesso SSH + sudo docker non-interattivo configurato per l'utente.
  • Branch feature/release multipli non protetti (nessuna evidenza di branch protection; molti branch cursor/* locali).

Rischio

ALTO (deploy non gated su un sistema già live).

Raccomandazione

GitHub Actions minima: (1) workflow PR/push → install, prisma generate, test backend+frontend, build; (2) workflow main → build immagini + push a registry (GHCR) e deploy che fa pull invece di buildare; (3) smoke test post-deploy (già quasi tutto presente nello script). Branch protection su main (require PR + status checks).

Effort

M.

4. Logging / Monitoring / Alerting

Stato attuale (evidenze)

  • Logging: common/logging/app-logger.service.ts — ConsoleLogger + append su file (APP_LOG_PATH, default /tmp/novarium-backend.log). Log testuali con timestamp/level/context; mai bloccante (try/catch).
  • Health/monitoring: health.controller.ts espone /api/health, /api/ready, /api/monitoring — lo snapshot include database, sendgrid, disco, certificati TLS, S3, AI, backup (health.service.ts:getMonitoringSnapshot), versione e gitSha.
  • Docker healthcheck su backend e website; deploy script verifica /api/health + gitSha post-deploy.
  • Script operativi: scripts/log-show-backend.sh, log-show-website.sh; journald per il poller IMAP (systemd timer).

Gap

  • Alerting assente: nessun uptime monitor esterno, nessun Sentry/error tracking, nessuna notifica se backup fallisce / certificato in scadenza / disco pieno — i check esistono ma nessuno li "sveglia".
  • Log su file dentro /tmp del container (in prod APP_LOG_PATH=/tmp/novarium-backend.log): effimero (perso a ricreazione container) e senza rotazione (crescita illimitata). Log non strutturati (no JSON), nessuna retention policy, docker logs non centralizzati.
  • /api/monitoring è pubblico (@Public() su tutto il controller): espone versioni, gitSha, stato disco/servizi → information disclosure utile a un attaccante.
  • Frontend senza error tracking (errori React solo in console).

Rischio

ALTO (mancanza di alerting su sistema live) — MEDIO per qualità/retention dei log.

Raccomandazione

Quick win: uptime monitor esterno (UptimeRobot/Healthchecks.io/BetterStack) su /api/health + check schedulato di /api/monitoring con alert email/webhook; spostare APP_LOG_PATH su volume persistente o loggare solo su stdout + docker logs con rotazione (max-size/max-file nel compose); proteggere /api/monitoring (auth ADMIN o IP allowlist in nginx). A seguire: log JSON + error tracking (Sentry self-hosted o SaaS).

Effort

S (uptime+alert+rotation+protezione endpoint) — M per log strutturati/error tracking.

Cosa serve per andare in produzione in sicurezza (checklist)

Il sistema risulta già live: questa checklist è la messa in sicurezza del live. Le voci ☐ sono da chiudere prima di considerare il sistema "in produzione consapevolmente".

Segreti e accessi

  • ☐ Ruotata SUPABASE_SERVICE_ROLE_KEY (e audit history per altri segreti commessi)
  • ☐ website.prod.env rimosso da git + history; .gitignore aggiornato
  • ☐ Verificati utenti BO attivi (disattivare i non usati), password admin robuste, JWT_SECRET prod ≥32 char random (non placeholder)
  • ☐ CORS_ORIGINS prod = solo https://bo.novarium.net

Dati e continuità

  • ☐ Backup automatico attivo e verificato (last_success recente in /api/monitoring)
  • ☐ Copia backup off-site (fuori dall'host)
  • ☐ Restore drill eseguito almeno una volta e documentato
  • ☐ prisma migrate deploy eseguito a ogni deploy (step bloccante)
  • ☐ Validazione parità legacy→prod archiviata

Osservabilità

  • ☐ Uptime monitor esterno su /api/health con alert (email/SMS/webhook)
  • ☐ Alert su fallimento backup, scadenza cert (<14gg), disco >80%, sendgrid down
  • ☐ Log persistenti con rotazione (niente /tmp del container)
  • ☐ /api/monitoring non pubblico

Hardening applicativo

  • ☐ Security headers (HSTS, nosniff, frame-ancestors, Referrer-Policy)
  • ☐ Throttling globale oltre agli endpoint auth
  • ☐ Password policy rafforzata
